# S12b — The verifier challenge set, tuning on dev, and the judge freeze

**Goal:** an honest, small check of the verifier on dev; a CI guard so the judge cannot change silently; one
frozen judge fingerprint; the test audit export gated on that freeze (ADR 0020, ADR 0011). Then tag
`prompts-frozen-v1`.

## Chronology

1. **Commit A (pre-registration).**
   - The scorer, the pass rule, the judge fingerprint and the challenge use case and CLI.
   - The 16-item set `challenge/dev-v1.jsonl` and the ADR 0020 draft.
   - All of this was committed before any model saw the set.
   - Items: AI-drafted, each one confirmed by the maintainer (one human rater).
   - An **AI** blind second rater (not a human, not an expert) agreed on 16/16 labels and on all 4
     overstated reasons. After its review, 7 claims were reworded for clarity; no label changed.
   - It flagged as ambiguous: ch04 and ch12 (could be read as overstated), ch10 (a null result rather
     than a reversal) and ch06 (also fits `certainty_inflation`).
2. **Commit B: v1 baseline.**

   | Field | Value |
   |---|---|
   | Verifier | `claude-opus-4-8` |
   | Prompt | the untuned S12a `VERIFY_PROMPT` |
   | Judge | `6d9996445668fa46…` |
   | Challenge set | `c7f12920…` |
   | Score | agree 15/16; 0 unsafe passes; 0 failures or absent evidence; 0 near; 0 supported-but-negated. **Rule met.** |
   | Table | supported → passed 4; overstated, contradicted and not_in_source → flagged 4 each |

   - The only disagreement was **ch04** (expected `not_in_source`, got `overstated` /
     `certainty_inflation`, quote located). The blind rater had flagged this item as ambiguous. It was
     flagged, not passed, so it is not an unsafe pass.
   - A read-only replay from the cache was **byte-identical** to the live attempt.
   - The attempt is kept locally under `var/challenge/`. It is not committed, because only the final run
     is recorded (D7).
   - Run count on the set: **1 of at most 2**.
3. **Step 5: failure analysis on natural dev pairs, no tuning.**
   - `run --dev` was run on all 8 dev questions, in strict and `over_eager` mode, with the v1 prompt. The
     answers were cache hits from S12a: the same prompts and models.
   - This gave **31 pairs**:

     | Disposition | Pairs |
     |---|---|
     | passed | 23 |
     | flagged | 4 |
     | needs_review | 4 |
     | failed | 0 |

   - Evidence: all 31 located; 0 near.
   - The maintainer reviewed them locally. Only these aggregate counts are committed (D12):
     - **Passed (23):** no substantive false pass was found.
     - **Flagged (4):** all four are defensible:
       - `surrogate_as_clinical`: 1;
       - `preclinical_to_clinical`: 1;
       - `other`: 2 (one omits a null RCT result; one has a part not in the cited source).
     - **Negated supported (4):** all `claim_shares_negation`. The claim itself is negative ("did not
       change", "did not significantly improve") and matches the abstract, so the guard's block is a
       false block. It is safe, because it fails closed to `needs_review`. D12's categories gained this
       one value; none of the four was `correct_block`, `unrelated_clause` or `unclear`.
     - **Near matches:** 0, so there was nothing to adjudicate.
     - **Minor:** absence claims ("the supplied papers do not report X") pass with a tangential quote, and
       one multi-source claim got different per-pair verdicts. Neither is a prompt problem.
   - **Decision (maintainer): no tuning.** The final prompt is v1. No negation or threshold change in S12b.
   - The `claim_shares_negation` false blocks go to the backlog, for a later ADR.
4. **Commit C: the recorded result and the attestation.**
   - `challenge run --record` ran as a read-only cache replay. The judge was unchanged, so the model did
     not see the set again.
   - It is byte-identical to the baseline attempt. Run count on the set: **1 of at most 2**.
   - `tests/arch/test_challenge_attestation.py` (I72) has no skip. A one-line edit to `verify_prompts.py`
     makes it fail with "made by another judge".
   - The test-id guard now has a planted challenge item, and a check that `challenge/` is scanned.
5. **Commit D: the freeze and the gated test export.**
   - **The freeze.** `freeze write` made `freeze/v1.json`, with judge `6d999644…` and
     `freeze_sha256 = ee8c5ce8…`. `app/freeze.py` pins its bytes (`FROZEN`) and sets
     `ACTIVE_FREEZE = "v1"`.
     - `tests/arch/test_active_freeze.py` (I73, no skip) checks every record against its pin and checks
       that the code is still the active judge.
   - **The test-split audit (I74).** `corpus audit-sheet` and `apply-audit` take `--split`.
     - For test, the container recomputes the active freeze (`active_freeze_sha256`). If it does not
       hold, the command refuses with `FreezeError` and names what changed.
     - The sheet's first line carries the seal and the freeze hash; apply checks it and stamps the freeze
       hash as `prompts_sha256`.
     - `--prompts-sha256` is refused for test and still required for dev. Dev is otherwise unchanged.
   - **Smoke test in the real environment:**
     - the gate opens on the committed code;
     - a one-line edit to `verify_prompts.py` closes it;
     - no test sheet was exported (the audits themselves are the author's, before S13).
   - **Deviation from D11.** "A test export never reads dev questions" was dropped:
     - Sources are split by cluster, not by question. In the real dataset, 403 of 654 dev sources were
       also retrieved by a test question, and the reverse also happens. So restricting the replay to one
       split's questions would lose abstracts.
     - The replay keeps only the wanted source ids, so reading another split's cached pool shows nothing
       new.
     - The guard that matters is that each sheet lists only its own split's sources. Tests cover that,
       for both splits.
6. **Implementation review, and freeze v1 redone (before the tag).** The triage table is below.
   - F1 was adopted, and the maintainer chose to redo v1.
     - `JUDGE_FILES` grew from 14 to 22 files: `canonical_json`, `base_llm_agent`, both codecs,
       `codec_support`, `messages`, `llm_runner` and `rulepack`.
     - Removed the v1 result and freeze, and re-recorded with `BCC_CACHE_MODE=read-only challenge run
       --record`, so no model was called.
     - The new result differs from the old one only in `judge_sha256` (`6d999644…` → `7d8d8f76…`).
     - `freeze write` produced `freeze_sha256 = c8b5383c…`, with the file pinned at `17705069…`.
     - Nothing had used the first v1: there was no tag and no test audit.

## Deviations from the plan (summary)

1. Outcomes carry no request or response hashes: LLM events carry none (I59). Provenance is the cache
   plus a byte-identical replay.
2. No `app/judge.py`: the fingerprint lives in `app/freeze.py`, next to the record it feeds.
3. No `record_run`: each attempt is written to `var/challenge/<judge>-<set>.json`.
4. `JUDGE_FILES` has 22 files: the planned list plus the rule pack and the request path (entry 6).
5. "No cross-split question reads" was dropped (entry 5). The guard is that each sheet lists only its own
   split's sources.
6. The D12 negation categories gained `claim_shares_negation`.

## Labels

One human (the maintainer) confirmed every label. An AI model did a blind second rating (16/16
agreement), and 7 claims were reworded with labels unchanged. Neither rater is an expert panel; backlog C6
asks for an independent human rater.
